# 项目交付闭环

当输入包含合同、任务书、技术要求、采购/招标文件、里程碑或验收指标时使用本文件。目标不是“尽量多实现”，而是：

```text
在全部有效强制要求、权限和安全边界满足的前提下，
用证据完成验收，并在可行方案中降低全生命周期资源成本。
```

硬要求之间逐项判断；成本、速度或综合得分不能补偿任一硬项失败。

## 0. 先确认工作对象存在

在建立完整控制记录前，用只读检查核对当前工作区、仓库/系统标识、模块、版本、合同与附件、数据/环境访问权以及可执行的测试入口。用户描述、README 或目录名只是线索，不是目标系统实际存在的证据。

若工作区为空、挂错项目、目标模块不存在或关键输入不可读，立即短路：列出已检查范围、缺失对象及最小启动条件；目标裁决为 `UNKNOWN`，执行状态按实际情况记为 `WAITING` 或 `STOPPED`。只允许继续不越界的发现和准备工作，不得凭空创建另一套系统来冒充“修改现有项目”。

## 1. 固定有效合同基线

先识别有权威性的输入：主合同、技术附件、图纸/接口协议、补充协议、已批准变更、验收规范和有权签收者。记录版本、日期和优先级。文件冲突或关键术语歧义会改变交付结果时，暴露冲突并请求有权主体裁决；不要自行选择更容易实现的一版。

把自然语言要求编译成稳定 ID：

| 字段 | 内容 |
|---|---|
| Requirement ID | 唯一编号 |
| Authority | 来源、版本、条款或批准变更 |
| Obligation | 不改变含义的简述 |
| Class | 强制功能、性能、接口、数据、安全、交付、运维；优化项；偏好；派生要求；假设 |
| Conditions | 环境、输入总体、负载模型、角色、冷/热状态、观察窗口、容差和例外 |
| Measure | 指标定义、单位、方向、阈值、抽样单位、聚合/分位方式和测量工具 |
| Acceptance protocol | 起止点、样本/流量选择、并发或到达率语义、预热、重复、排除规则、最小暴露量、统计判据和校准要求 |
| Evidence | 能证明通过的测试或验收动作 |
| Owner | 实现责任人及验收责任人 |
| Status | unknown、planned、implemented、verified-pass、verified-fail、waived-by-change |

指标不明确但不会改变设计时，可标为候选并继续可逆工作；会改变架构、预算、风险或验收时，只能做有上限的调查，不能发明正式阈值。

对“零故障、零越权”等零事件指标，必须明确覆盖范围、暴露量、检测灵敏度、失败分类和通过规则；有限样本中未观察到事件不自动证明真实发生率为零。并发量、到达率、同时在线数和总请求数不得混写；延迟必须固定计时边界、客户端/服务端位置和统计窗口；正确率必须固定判定单位、分母、样本集与裁决者。

用户或合同给出的期限是必须检查的约束，不自动构成 Agent 的交付承诺。只有在有效范围、基线、依赖、人员/算力、关键路径、验证与缓冲均有依据后，才能声明排期可行；证据不足时单独标记 `schedule feasibility: UNKNOWN`，给出验证排期所需的最小输入，不把条件性计划写成“保证完成”。

将约束分为：

- **过程不变量**：安全、权限、隐私、合规、数据完整性等全程不得失守的条件；
- **终端验收项**：只要求最终交付状态达标，允许中间路径和局部实现自适应；
- **优化项**：在可行集合内比较的时间、成本、资源、维护性或体验。

“不打折扣”锁定前两类，不意味着把实现路径、工具或所有软指标永久锁死。

## 2. 建立基线和三个事实面

在改动前复现当前行为，记录代码提交、依赖、数据、模型、硬件、配置、测试环境、现有指标和已知缺陷。区分已通过、已失败和未知；历史报告不能自动当作本次证据。

复杂项目尽量只维护三个事实面：

1. **Project control**：当前唯一有效的目标、合同版本、范围、预算、授权、阶段、安全状态和下一门禁。
2. **Traceability**：`要求 → 资源/设计 → 实现位置 → 测试 → 原始证据 → 状态` 的双向映射。
3. **Verification**：本次实际使用的版本、环境、数据、命令、结果、证据位置、限制和复现方法。

变更发生时增加变更记录；临近正式验收时从三个事实面生成验收包。不要创建互相冲突的平行真相文件。

## 3. 盘点、组合并裁决资源复用

按发现成本从低到高检查：项目内已有实现、当前平台能力与依赖、标准库/成熟组件、可适配的内部资源、新外部依赖或服务、自建。这个顺序只用于发现，不保证前者一定更优。

候选单项或组合先逐项通过非补偿门禁：

- 每项资源能胜任拟分配角色，组合后能覆盖对应要求，且两层能力都有可验证证据；
- 许可证、知识产权、来源和交付方式符合合同；
- 与目标接口、数据、环境、性能和维护周期兼容；
- 安全、隐私、供应链和锁定风险可接受；
- 能在本项目验收环境中被观察、测试、拒绝和替换；
- 维护主体、故障路径、回退和退出方案明确。

单项资源不必独立完成整个要求，但不得承担未经验证的角色。若多个现有资源可互补覆盖要求，或能在同等验收水平下降低成本/风险，读 [资源综合与结构增益](resource-synthesis.md)，把组合系统作为一个有稳定 ID 的设计节点；检查共同依赖、错误相关性、路由、仲裁、隔离、切换和协调开销。若一个单体已更经济地满足全部硬项，优先使用单体。

通过后再比较全生命周期成本：

```text
获取/许可 + 适配 + 集成 + 验证 + 运行
+ 审计 + 维护 + 升级 + 替换/退出
```

证据不足时做有时间、费用和变更范围上限的适配探针。GitHub stars、宣传、他项测试或“大家都在用”只是发现信号，不是本项目的通过证据。记录采用方式：原样复用、包装适配、维护分叉、只作设计参考或拒绝。

若选择组合，除各组件角色测试外，还必须在合同条件下按预先冻结的关系比较指定对象、与各声明相关的最佳获准单体或非支配基线集合和组合系统，执行端到端、组件消融、共同错误和必要的故障注入。故障注入只在明确获准的非生产环境或隔离演练中进行，预先限制影响范围并准备恢复；无法安全注入时使用模拟故障或故障替身并记录证据局限。结构增益裁决不能替代任何合同硬项；隐藏的强模型、人工或外部服务必须计入能力来源和成本。

## 4. 过可观测、可控与可达门禁

对每个硬要求检查：

- 现有测量能否在要求指定条件下发现主要失败，而不是只测到方便的代理量？
- 可用代码入口、人员、工具和权限能否实际影响目标？
- 约束下是否至少存在一个可行方案？关键依赖或动作饱和时会怎样？
- 子系统局部通过是否可能损害全局指标？接口和协调责任是否明确？

先验证最危险、最不确定或最可能使整体不可行的假设。若目标不可测或不可达，先补观测、换控制杠杆或报告可行性缺口；更多代码不能修复结构性不可达。

## 5. 设计并执行分段闭环

建立 `要求 → 设计决策 → 组件/资源 → 代码位置 → 测试` 映射后，以端到端可验证的小批次实现。每批必须推进至少一个原始要求，并预先定义：

- 预计改变的目标误差和因果理由；
- 允许触碰的文件、系统和外部边界；
- 单次和累计时间、重试、费用与算力上限；
- 通过、失败、无效测量、回退和升级条件；
- 该批最多能声明任务、阶段还是总目标完成。

优先做最小忠实变更：足以验证当前因果假设，同时完整处理该切片必需的正常路径、错误路径、边界和测试。不要借“先做 MVP”永久删除合同项，也不要借“做完整”自动扩建未授权功能。

每次非平凡改动后读取实际状态。若同类问题重复出现，把它优先变成可执行测试、类型/模式约束、接口边界、运行时保护或审批门，而不是只增加提示词。

## 6. 累积验证并排练验收

测量方式必须匹配失效域：

| 失效域 | 典型证据 |
|---|---|
| 纯逻辑、计算和规则 | 单元测试、性质测试、确定性检查 |
| 模块接口、权限和依赖 | 集成测试、契约测试、拒绝路径 |
| 真实用户或业务流程 | 端到端运行、实际操作记录 |
| 性能、精度、可靠性和资源 | 固定数据/负载、代表环境、重复测量、统计与原始日志 |
| 故障、安全、资金或生产路径 | 在授权非生产环境中的故障注入或模拟、隔离、恢复、回退及审批证据 |
| 视觉或交互结果 | 真实渲染、截图/交互检查和可访问性验证 |

计划中的测试、仓库里存在的测试和本次实际运行的测试是三种状态。退出码为零时仍确认测试确实被发现、没有关键跳过，且断言覆盖合同指标。第三方组件自己的测试不能替代集成证据。

区分开发/校准数据与正式验收数据，固定版本、哈希、访问和揭盲规则。正式验收集一旦被用于裁决，不得继续据其结果调参后在同一数据上宣称独立通过；若候选发生实质调整，应按验收协议启用新的未触碰样本或记录为探索性复测。

正式验收前，在合同指定版本、环境、数据、角色和观察窗口中重跑验收。实现者的完成判断与有权验收者的接受分开记录。

## 7. 变更控制

任何改变范围、功能、指标、阈值、期限、费用、外部影响、风险或验收方法的请求都执行：

```text
记录请求 → 定位受影响要求与下游实现/测试
→ 估算时间、成本、风险和证据影响 → 给出选项与推荐
→ 获得有权主体决定 → 发布新基线版本
→ 更新追踪、计划和验证
```

变更未批准时可继续不受影响的本地可逆工作，但不得越过争议边界。豁免会改变有效基线，不证明旧要求已经通过。多 Agent 工作只设一个合同状态写入者；子任务提交证据，无权独自改目标或宣布总项目完成。

## 8. 裁决与安全停止

分别报告两个轴，避免把“目标是否达成”和“当前是否还在执行”混为一谈：

- **目标裁决**：`PASS` 表示该边界内全部强制项有合格证据、硬边界未突破、无未授权偏差且所需验收已完成；`FAIL` 表示当前候选被有效证据证明不满足硬项；`UNKNOWN` 表示证据不足或外部结果不明。
- **执行状态**：`RUNNING` 表示仍在授权和资源包络内推进；`WAITING` 表示已安全保持、正等待明确输入/权限/外部结果；`STOPPED` 表示因预算、风险、依赖、不可行或有权主体决定而结束本轮执行。

两轴可以组合，例如目标 `UNKNOWN`、执行 `STOPPED`；不得用“已停止”暗示目标失败，也不得用局部 `PASS` 掩盖执行已越界。

任务或阶段 `PASS` 不代表总项目 `PASS`。需要等待或停止时，冻结新增范围、支出和外部写入，保留最后验证版本、差异、日志和原始证据，撤销临时权限，并列出恢复所需的最小决定。

## 推荐交付摘要

最终回复优先给出结果，而后包含：

1. 当前裁决及层级；
2. 已满足、失败、未知和经批准变更的要求；
3. 版本、环境、测量、关键数值和证据位置；
4. 实际资源消耗及相对预算；
5. 残余风险、回退/运行方法和需要验收者作出的下一决定。
